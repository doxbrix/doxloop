# Docusaurus project format

A Doxloop-created Docusaurus project contains:

```text
.
├── .doxloop/project.json
├── docs/
│   ├── index.md
│   └── quickstart.md
├── src/css/custom.css
├── docusaurus.config.js
├── sidebars.js
└── package.json
```

`docusaurus.config.js` owns site metadata, presets, plugins, theme configuration,
and the docs route. `sidebars.js` owns explicit or autogenerated documentation
navigation. The default Doxloop scaffold uses:

```js
export default {
  docs: [{ type: 'autogenerated', dirName: '.' }],
}
```

With an autogenerated sidebar, use directories and page frontmatter to control
organization:

```markdown
---
title: Configure authentication
description: Require API keys for protected requests.
sidebar_position: 3
sidebar_label: Authentication
slug: /guides/authentication
---
```

An explicit sidebar may combine native item types:

```js
export default {
  docs: [
    'index',
    {
      type: 'category',
      label: 'Guides',
      items: ['guides/authentication'],
    },
    {type: 'link', label: 'Status', href: 'https://status.example.com'},
  ],
}
```

String items and `{type: 'doc', id: '…'}` refer to document IDs, not URL slugs.
Inspect existing `id` and `slug` frontmatter before editing explicit entries.
Other native item types include `ref`, `autogenerated`, and `html`; preserve
their existing fields and consult the project's installed Docusaurus
documentation before introducing one.

For autogenerated directories, preserve existing `_category_.json`, `.yml`, or
`.yaml` metadata and its label, position, collapsibility, and generated-index
settings. Do not introduce category metadata unless the information
architecture needs it. Do not create `docs.json` for Docusaurus navigation.

## Application brand mapping

Apply captured product values through Docusaurus-native files:

- copy logos and favicons to `static/img` and fonts to `static/fonts`;
- set `favicon` and `themeConfig.navbar.logo.src`/`srcDark` in
  `docusaurus.config.js`;
- set `themeConfig.colorMode.respectPrefersColorScheme` when the product uses
  system mode;
- define the primary palette and font variables in `src/css/custom.css`;
- add `@font-face` only for copied, redistributable local fonts.

```css
:root {
  --ifm-color-primary: #4f46e5;
  --ifm-color-primary-dark: #4338ca;
  --ifm-color-primary-light: #6366f1;
  --ifm-font-family-base: 'Brand Sans', system-ui, sans-serif;
  --ifm-heading-font-family: 'Brand Display', var(--ifm-font-family-base);
  --ifm-font-family-monospace: 'Brand Mono', ui-monospace, monospace;
}

[data-theme='dark'] {
  --ifm-color-primary: #818cf8;
}
```

Use product design tokens for palette variants when available. Do not generate
unverified shades merely to fill every Infima variable; leave unsupported
variants on the theme defaults. Check primary links and controls for WCAG-AA
contrast in both modes. `npm run build` plus visual preview remain the acceptance
checks.
